## Overview

This project demonstrates the provisioning of an AWS DynamoDB table using Terraform against a LocalStack environment. The implementation covers writing a Terraform resource configuration, diagnosing and resolving provider duplication errors introduced by a pre-existing `provider.tf`, and completing the full Terraform lifecycle: `init`, `validate`, `plan`, and `apply`.

| Attribute | Details |
|---|---|
| **Cloud Provider** | AWS (via LocalStack) |
| **IaC Tool** | Terraform |
| **Resource Provisioned** | AWS DynamoDB Table |
| **Table Name** | `datacenter-users` |
| **Primary Key** | `datacenter_id` (String) |
| **Billing Mode** | `PAY_PER_REQUEST` |
| **Environment** | LocalStack (`http://aws:4566`) |
| **Working Directory** | `/home/bob/terraform` |

## Problem Statement

The Nautilus DevOps team requires a DynamoDB table for storing datacenter user data. The table must meet the following specifications:

* **Table Name:** `datacenter-users`
* **Primary Key (Hash Key):** `datacenter_id` (Type: String)
* **Billing Mode:** `PAY_PER_REQUEST`

The task must be completed using Terraform with all configuration written exclusively in `main.tf`. No additional `.tf` files should be created beyond what already exists in the working directory.

---

## Solution Architecture

The solution uses a single Terraform resource block authored in `main.tf`. A pre-existing `provider.tf` in the working directory already defines the `terraform` backend block, the `required_providers` constraint, and the AWS provider configuration pointing to LocalStack endpoints. After encountering duplicate configuration errors on the first `terraform init` attempt, `provider.tf` was inspected to understand the conflict. The fix was to strip `main.tf` down to the resource block only, delegating all provider and backend concerns to `provider.tf`.

```
/home/bob/terraform/
├── provider.tf       # Pre-existing: backend, required_providers, and AWS provider config
├── main.tf           # Authored: aws_dynamodb_table resource definition only
└── README.MD         # Pre-existing: task context
```

### Step 2: Author main.tf with Full Terraform Configuration

Write `main.tf` using a heredoc. At this point, without having read `provider.tf`, the configuration includes a `terraform` block with `required_providers`, a `provider "aws"` block, and the `aws_dynamodb_table` resource block.

```bash
cat > main.tf << 'EOF'
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

resource "aws_dynamodb_table" "datacenter_users" {
  name         = "datacenter-users"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "datacenter_id"

  attribute {
    name = "datacenter_id"
    type = "S"
  }
}
EOF
```

## Errors and Resolutions

### Error 1: Duplicate required_providers Configuration

| Field | Details |
|---|---|
| **Error Message** | `Duplicate required providers configuration` |
| **Reported File** | `provider.tf` line 2 |
| **Triggered By** | `terraform init` (Step 5) |
| **Root Cause** | `main.tf` declared a `terraform { required_providers {} }` block while `provider.tf` already contained an identical declaration. Terraform enforces a single `required_providers` block per module. All `.tf` files in a directory are merged into one module at runtime, making duplicate declarations across files a fatal initialization error. |
| **Resolution** | Removed the `terraform { required_providers {} }` block from `main.tf` after reading `provider.tf` in Step 6, leaving provider version constraints exclusively in `provider.tf`. |

---

### Error 2: Duplicate Provider Configuration

| Field | Details |
|---|---|
| **Error Message** | `Duplicate provider configuration` |
| **Reported File** | `provider.tf` line 10 |
| **Triggered By** | `terraform init` (Step 5) |
| **Root Cause** | `main.tf` declared `provider "aws" { region = "us-east-1" }` while `provider.tf` already declared a default (non-aliased) `provider "aws"` block with LocalStack endpoint overrides and credential-skip flags. Terraform does not permit two default provider configurations for the same provider within a single module. |
| **Resolution** | Removed the `provider "aws"` block from `main.tf` after reading `provider.tf` in Step 6. The `provider.tf` configuration is the authoritative provider definition for this workspace and contains the LocalStack routing that makes the environment functional. |

## Best Practices Applied

* **Audit the workspace before writing configuration:** Running `ls -la` at the start revealed `provider.tf` was already present. While its full contents were not inspected until after the `terraform init` failure, awareness of its existence is the first signal that the workspace is pre-configured and warrants investigation before writing new provider declarations.

* **Verify file content after every write:** Running `cat main.tf` immediately after each heredoc write (Steps 3 and 8) confirms the file content is exactly as intended before any Terraform commands are executed. This prevents silent file write failures or heredoc delimiter errors from propagating into the Terraform lifecycle.

* **Diagnose before fixing:** Reading `provider.tf` after the `terraform init` failure (Step 6) provided the exact information needed to determine which declarations in `main.tf` were redundant. Attempting to fix the conflict without reading `provider.tf` first could have produced a partial fix or introduced a different error.

* **Separation of concerns across `.tf` files:** Provider-level configuration (`terraform`, `required_providers`, `provider`) lives in `provider.tf`, while resource definitions are isolated in `main.tf`. This mirrors production conventions where platform teams own provider configuration centrally and application teams own resource definitions independently.

* **Full Terraform lifecycle execution:** The workflow follows `init` -> `validate` -> `plan` -> `apply` without skipping steps. Each stage acts as a progressive gate: `validate` catches syntax and schema errors, `plan` documents intent and surfaces logic issues, and `apply` executes only after both earlier stages pass cleanly.

* **PAY_PER_REQUEST billing mode:** Using `PAY_PER_REQUEST` eliminates the need to pre-provision read and write capacity units. This is appropriate for workloads with unpredictable or variable traffic and removes capacity management as an operational concern.

* **Lock file retention:** The `.terraform.lock.hcl` file generated by `terraform init` pins `hashicorp/aws` at version `5.91.0`. Committing this file to version control ensures every subsequent `terraform init` in any environment installs the exact same provider version, eliminating version drift across team members and CI pipelines.

## Lessons Learned

* **All `.tf` files in a directory are merged into a single module.** Terraform does not treat each `.tf` file as an independent configuration. Every file in the working directory contributes to one unified module at runtime. Writing a `terraform` block or `provider` block in `main.tf` while an existing `provider.tf` already declares the same blocks is a guaranteed initialization failure. Always run `ls -la *.tf` and read the contents of all existing files before writing new configuration in a shared workspace.

* **`terraform init` performs configuration validation before downloading plugins.** The error message `The Terraform configuration must be valid before initialization so that Terraform can determine which modules and providers need to be installed` confirms that Terraform runs a structural validation pass before any network activity. A conflicting configuration blocks even the provider download stage, so configuration correctness is a prerequisite for all subsequent lifecycle commands.

* **The error message identifies the file Terraform encountered second, not the file to fix.** Both errors reported `provider.tf` as the location of the duplicate. This is because Terraform had already registered the declarations from `main.tf` and then encountered `provider.tf` as the conflicting second occurrence. The actual fix was to remove the declarations from `main.tf`, not `provider.tf`. Misreading this can lead to removing configuration from the wrong file.

* **Pre-existing `provider.tf` configurations in shared workspaces encode environment-specific routing that must not be overridden.** The `provider.tf` in this workspace routes all AWS API calls to LocalStack via `http://aws:4566`, and includes credential-skip flags required for the simulated environment. Had the `provider "aws"` block in `main.tf` survived into `apply`, API calls would have been directed to real AWS endpoints, causing authentication failures. Preserving `provider.tf` intact was essential to maintaining correct environment behavior.

* **Read existing workspace files before writing new configuration in any shared or platform-managed environment.** The root cause of the initialization failure was writing provider-level declarations without first confirming whether they already existed in the workspace. In production environments, working directories are often pre-seeded with backend, provider, and variable configurations by platform teams. Reading these files before authoring new `.tf` files is a non-negotiable step in any team-based Terraform workflow.
