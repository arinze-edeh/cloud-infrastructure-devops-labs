## Overview

This repository documents the end-to-end provisioning of an **AWS CloudWatch Metric Alarm** using **Terraform** as the sole Infrastructure as Code (IaC) tool. The implementation was executed within a LocalStack-backed AWS emulation environment, simulating a production AWS account for the Nautilus DevOps team's monitoring stack.

The alarm monitors **EC2 CPU Utilization** and triggers when utilization exceeds **80%** over a single **5-minute** evaluation window. This serves as a foundational building block for the team's broader observability and incident response posture.

---

## Problem Statement

The Nautilus DevOps team is establishing automated monitoring across their AWS infrastructure. The immediate requirement is to provision a CloudWatch alarm that:

* Monitors the CPU utilization metric of EC2 instances
* Triggers an alert condition when CPU utilization surpasses **80%**
* Evaluates the metric over a **5-minute (300-second) period**
* Uses a **single evaluation period** to minimize alert latency
* Is fully managed and reproducible through Terraform, with no manual console configuration

The entire configuration must reside in a single `main.tf` file within the designated Terraform working directory at `/home/bob/terraform`.

  namespace           = "AWS/EC2"
  period              = 300
  statistic           = "Average"
  threshold           = 80
  alarm_description   = "Alarm when EC2 CPU utilization exceeds 80%"

## Best Practices Applied

* **Single-file resource separation:** The alarm resource is defined in `main.tf`, kept separate from `provider.tf`. This follows the Terraform convention of separating provider configuration from resource definitions, improving maintainability and readability.

* **Provider version pinning:** The AWS provider is locked to `5.91.0` in both `required_providers` and enforced via `.terraform.lock.hcl`. This prevents unintended provider upgrades that could introduce breaking changes.

* **Validate before apply:** Running `terraform validate` prior to `terraform apply` catches configuration errors early in the pipeline without touching infrastructure. In CI/CD pipelines, this should be a mandatory gating step.

* **Declarative infrastructure intent:** All alarm parameters are explicitly declared rather than relying on provider defaults. This makes the configuration self-documenting and prevents unexpected behavior from default value changes across provider versions.

* **Post-apply verification:** The alarm was confirmed independently using the AWS CLI (`describe-alarms`) rather than trusting solely on Terraform's apply output. This is a production-grade verification habit that catches partial provisioning failures.

* **Heredoc for file authoring:** Using `cat > main.tf << 'EOF'` with a quoted heredoc delimiter prevents variable and command substitution within the file content, ensuring the HCL is written exactly as intended.

## Lessons Learned

1. **`INSUFFICIENT_DATA` is normal for new alarms.** A freshly created CloudWatch alarm will always show `StateValue: INSUFFICIENT_DATA` and `StateReason: "Unchecked: Initial alarm creation"`. This is not an error. The state will transition to `OK` or `ALARM` only after the first metric evaluation period completes with actual data points.

2. **`treat_missing_data` is silently injected by the provider.** Even though this field was not declared in `main.tf`, Terraform automatically applied the provider default of `"missing"`. Teams should be explicit about this field in production configurations to avoid ambiguity during incident response.

3. **LocalStack endpoint routing requires `--endpoint-url` in every AWS CLI command.** When validating resources outside of Terraform, every AWS CLI call must include `--endpoint-url=http://aws:4566`. Forgetting this will cause the CLI to attempt a real AWS API call and fail.

4. **The `.terraform.lock.hcl` file must be committed to version control.** As noted in the `terraform init` output, this file guarantees identical provider selections across all environments. Excluding it from source control is a common operational mistake.

5. **`-auto-approve` is appropriate only in controlled environments.** In production pipelines, `terraform apply` should require explicit plan review and approval gating. The `-auto-approve` flag was used here because the environment is a sandboxed lab with no risk of unintended resource modification.

## Errors and Resolutions

No errors were encountered during this implementation. The following table documents anticipated failure modes and their resolutions for operational reference.

| Scenario | Symptom | Root Cause | Resolution |
|---|---|---|---|
| Provider not found | `Error: Failed to query available provider packages` | Network isolation or Terraform registry unreachable | Ensure outbound HTTPS to `registry.terraform.io` is permitted, or use a private mirror |
| LocalStack connection refused | `Error: Post "http://aws:4566/": dial tcp: connection refused` | LocalStack container not running | Start the LocalStack container and confirm DNS resolution of `aws` hostname |
| Alarm name conflict | `Error: creating CloudWatch Metric Alarm: AlarmAlreadyExists` | A prior `terraform apply` or manual creation left a conflicting alarm | Run `terraform destroy` or manually delete the alarm before re-applying |
| Missing required field | `Error: Missing required argument` | A required field (`alarm_name`, `comparison_operator`, etc.) was omitted from `main.tf` | Add the missing field and re-run `terraform validate` followed by `terraform apply` |
| Incorrect file name | Resource not created | A `.tf` file with a name other than `main.tf` was used | Rename the file to `main.tf` per the task constraint |
