## Project Overview

This document covers the end-to-end provisioning of an AWS Security Group for the **Nautilus App Servers** using **Terraform** as part of a phased infrastructure migration to AWS. The task is scoped to the `us-east-1` region and uses the default VPC. All configuration is authored in a single `main.tf` file located in `/home/bob/terraform`, following the task specification precisely.

| Field | Detail |
|---|---|
| **Cloud Provider** | Amazon Web Services (AWS) |
| **Region** | `us-east-1` |
| **IaC Tool** | Terraform (HashiCorp) |
| **Provider Version** | `hashicorp/aws v5.91.0` |
| **Working Directory** | `/home/bob/terraform` |
| **Configuration File** | `main.tf` |
| **Resource Type** | `aws_security_group` |
| **Resource Name** | `nautilus_sg` |

---

## Problem Statement

The Nautilus DevOps team is executing a large-scale migration of their on-premises infrastructure to AWS. To reduce risk and ensure operational continuity, the team has adopted an incremental migration strategy, decomposing the full migration into small, independently deliverable units.

This phase focuses on establishing the foundational network security layer by provisioning a Security Group that governs inbound traffic to the Nautilus App Servers. The group must permit HTTP traffic on port `80` and SSH access on port `22`, both accepting traffic from any source IP (`0.0.0.0/0`).

The infrastructure must be:

* **Reproducible** using declarative IaC (Terraform)
* **Traceable** through Terraform state
* **Confined** to a single `main.tf` configuration file as stipulated by the task

---

## Solution Architecture

The solution provisions a single AWS Security Group within the default VPC of the `us-east-1` region. The security group is defined declaratively using the `aws_security_group` Terraform resource, with two explicit ingress rules and no custom egress rules (AWS allows all outbound traffic by default).

```
+----------------------------------------------------------+
|                    AWS Default VPC                       |
|                    (us-east-1)                           |
|                                                          |
|   +--------------------------------------------------+   |
|   |         Security Group: nautilus-sg              |   |
|   |                                                  |   |
|   |   Ingress Rules:                                 |   |
|   |   * TCP Port 80  (HTTP)  CIDR: 0.0.0.0/0        |   |
|   |   * TCP Port 22  (SSH)   CIDR: 0.0.0.0/0        |   |
|   |                                                  |   |
|   |   Egress Rules:                                  |   |
|   |   * Default: All traffic allowed (AWS default)   |   |
|   +--------------------------------------------------+   |
+----------------------------------------------------------+
```

## Implementation Guide

### Step 1: Create the Terraform Working Directory

The working directory `/home/bob/terraform` serves as the Terraform root module directory. Navigate to this directory and create the `main.tf` configuration file.

```bash
touch main.tf
```

*Screenshot: Terminal showing successful creation of `main.tf` with no errors.*

> **Why `touch` first?** Using `touch` explicitly creates an empty file before writing content, which is a deliberate and auditable approach. This confirms write access to the directory before committing configuration content.

---

### Step 2: Author the Terraform Configuration

Write the complete Terraform configuration for the AWS Security Group into `main.tf` using a heredoc redirect. This approach ensures the entire configuration block is written atomically in a single shell operation.

```bash
cat > main.tf << 'EOF'
resource "aws_security_group" "nautilus_sg" {
  name        = "nautilus-sg"
  description = "Security group for Nautilus App Servers"

  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  ingress {
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
EOF
```

Verify the file contents are written correctly:

```bash
cat main.tf
```

Expected output:

```hcl
resource "aws_security_group" "nautilus_sg" {
  name        = "nautilus-sg"
  description = "Security group for Nautilus App Servers"

  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  ingress {
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

*Screenshot: Terminal output of `cat main.tf` confirming the complete configuration block.*

### Step 4: Validate the Configuration

Run `terraform validate` to perform a static syntax and semantic check on the configuration without making any API calls to AWS.

```bash
terraform validate
```

Expected output:

```
Success! The configuration is valid.
```

*Screenshot: Terminal showing `Success! The configuration is valid.` output from `terraform validate`.*

> **Why validate before plan?** `terraform validate` catches HCL syntax errors, invalid resource attribute names, and type mismatches early, before any remote API calls are made. This saves time in automated pipelines where a failed `plan` would otherwise consume billable API quota.

## Best Practices Applied

The following engineering best practices were observed during this implementation:

* **Single configuration file discipline:** The entire resource definition is contained in one `main.tf` file as required, keeping the root module flat and auditable.

* **Heredoc for atomic file writes:** Using `cat > main.tf << 'EOF' ... EOF` writes the entire configuration block in a single atomic shell operation, preventing partial writes.

* **Content verification after write:** Immediately running `cat main.tf` after writing confirms the file contents match the intended configuration before proceeding.

* **Sequential IaC workflow:** The standard `init > validate > plan > apply` sequence was followed without skipping steps. `validate` provides a fast, zero-cost check; `plan` provides a human-readable change preview.

* **State inspection post-apply:** Running `terraform state list` and `terraform state show` after apply confirms that Terraform's state file accurately reflects the provisioned infrastructure, closing the verification loop.

* **Provider lock file integrity:** The `.terraform.lock.hcl` file generated by `terraform init` pins the provider to `hashicorp/aws v5.91.0`, ensuring deterministic behavior across executions and environments.

## Lessons Learned

**1. `terraform validate` saves time in iterative workflows.**
Running validate before plan prevents unnecessary round-trips to the AWS API for configurations with syntax or schema errors. In pipelines, this translates to faster feedback and lower API call overhead.

**2. `terraform state show` is the ground truth for provisioned resources.**
The state file is Terraform's source of truth. After any apply, inspecting state confirms the exact attributes AWS assigned (IDs, ARNs, VPC associations), which are critical for downstream resource references.

**3. Heredoc file writes are more reliable than multi-line echo chains.**
Using `cat > file << 'EOF'` with a quoted delimiter (`'EOF'`) prevents variable expansion inside the block, ensuring special characters like `$` are written literally. This is important for HCL files that may contain variable references.

**4. Egress rules default to empty in Terraform, not open.**
When no `egress` block is defined in the `aws_security_group` resource, Terraform creates the group with no egress rules in state (`egress = []`). AWS itself still applies its default allow-all outbound behavior at the platform level, but Terraform does not manage or track it. Explicitly defining egress rules is recommended for production environments to maintain full IaC control over outbound traffic.

**5. The `-out` flag for `terraform plan` should be standard in non-interactive workflows.**
In this task, `terraform apply` was run interactively without a saved plan file. In production CI/CD pipelines, `terraform plan -out=tfplan` followed by `terraform apply tfplan` eliminates the risk of plan drift between the review stage and the apply stage.

## Errors Encountered and Resolutions

No errors were encountered during this implementation. The full workflow from `touch main.tf` through `terraform state show` completed successfully on the first execution. The `terraform validate` step confirmed configuration correctness before any AWS API calls were made, and `terraform apply` completed resource creation in approximately 1 second.

> If you encounter errors during reproduction, refer to the checklist below:

| Symptom | Likely Cause | Resolution |
|---|---|---|
| `Error: No valid credential sources found` | AWS credentials not configured | Set `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` environment variables or configure `~/.aws/credentials` |
| `Error: Provider hashicorp/aws not found` | `terraform init` not run | Run `terraform init` before any other Terraform commands |
| `Error: Invalid resource type` | Typo in resource block type | Run `terraform validate` and correct the HCL syntax |
| `Error: Security group already exists` | Resource with same name exists in the VPC | Import the existing resource using `terraform import` or destroy it first |
| `Error: creating Security Group: operation error` | Insufficient IAM permissions | Verify the IAM principal has `ec2:CreateSecurityGroup` and `ec2:AuthorizeSecurityGroupIngress` permissions |
