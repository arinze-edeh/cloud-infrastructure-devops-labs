## Overview

This repository documents the end-to-end provisioning of an AWS Identity and Access Management (IAM) policy using Terraform as the Infrastructure as Code (IaC) tool. The policy enforces least-privilege, read-only access to the Amazon EC2 console, enabling authorized users to view instances, AMIs, and snapshots without the ability to modify or delete any resources.

The implementation targets a LocalStack-backed AWS simulation environment, making it suitable for local development, testing, and CI/CD pipelines before promotion to production AWS accounts.

---

## Problem Statement

When establishing infrastructure on AWS, IAM is among the first and most critical services to configure. IAM facilitates the creation and management of user accounts, groups, roles, policies, and other access controls. The Nautilus DevOps team is in the process of configuring these resources and has defined the following requirement:

**Create an IAM policy named `iampolicy_rose` in the `us-east-1` region using Terraform. The policy must grant read-only access to the EC2 console, specifically allowing users to view all instances, AMIs, and snapshots.**

The Terraform working directory is `/home/bob/terraform`. The resource definition must be created exclusively in `main.tf`. No additional `.tf` files are to be created for this task.

### Step 5: Author the IAM Policy Resource

Create `main.tf` in the working directory with the `aws_iam_policy` resource definition. The policy grants read-only access to EC2 resources using wildcard action patterns scoped to `Describe*`, `Get*`, and `List*`.

```bash
cat > main.tf << 'EOF'
resource "aws_iam_policy" "iampolicy_rose" {
  name        = "iampolicy_rose"
  description = "Read-only access to EC2 console including instances, AMIs, and snapshots"

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Action = [
          "ec2:Describe*",
          "ec2:Get*",
          "ec2:List*"
        ]
        Resource = "*"
      }
    ]
  })
}
EOF
```

Verify the file was written correctly:

```bash
cat main.tf
```

**Output:**
```hcl
resource "aws_iam_policy" "iampolicy_rose" {
  name        = "iampolicy_rose"
  description = "Read-only access to EC2 console including instances, AMIs, and snapshots"

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Action = [
          "ec2:Describe*",
          "ec2:Get*",
          "ec2:List*"
        ]
        Resource = "*"
      }
    ]
  })
}
```

> **Design rationale:** Using `jsonencode()` keeps the IAM policy inline with the Terraform resource block, avoiding the need for a separate JSON file. The wildcard patterns `ec2:Describe*`, `ec2:Get*`, and `ec2:List*` cover all current and future EC2 read-only actions, matching AWS managed policy conventions for read-only console access.

## IAM Policy Definition

The following is the complete IAM policy document provisioned by this configuration:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ec2:Describe*",
        "ec2:Get*",
        "ec2:List*"
      ],
      "Resource": "*"
    }
  ]
}
```

| Field | Value | Purpose |
|---|---|---|
| `Version` | `2012-10-17` | Current IAM policy language version |
| `Effect` | `Allow` | Permits the listed actions |
| `Action: ec2:Describe*` | All EC2 Describe actions | View instances, AMIs, snapshots, security groups, etc. |
| `Action: ec2:Get*` | All EC2 Get actions | Retrieve console screenshots, password data, etc. |
| `Action: ec2:List*` | All EC2 List actions | Enumerate snapshots, images, and related resources |
| `Resource` | `*` | Applies to all EC2 resources in the account |

## Best Practices Applied

***Provider Version Pinning***
The AWS provider is locked to `version = "5.91.0"` in `provider.tf` and further enforced by the `.terraform.lock.hcl` file. This prevents unintended provider upgrades that could introduce breaking changes in CI/CD pipelines or team environments.

***Separation of Concerns***
Provider configuration (`provider.tf`) is kept separate from resource definitions (`main.tf`). This standard Terraform project structure improves readability and allows provider configuration to be shared across multiple resource files without duplication.

***Pre-Apply Validation Workflow***
The implementation followed the canonical Terraform workflow: `init` then `validate` then `plan` then `apply`. Running `terraform validate` before `terraform plan` catches syntax errors early and without the overhead of an API call to the provider.

***Independent Verification***
After `terraform apply`, the resource was verified through two independent methods: `terraform state list` (confirming IaC state integrity) and `aws iam list-policies` (confirming real infrastructure existence). This dual verification approach is critical in production workflows where state drift must be detectable.

***Least-Privilege Policy Design***
The IAM policy grants only read-only permissions (`Describe*`, `Get*`, `List*`) and does not include any write, delete, or administrative actions. This adheres to the AWS principle of least privilege and aligns with AWS managed policy conventions (e.g., `AmazonEC2ReadOnlyAccess`).

***Use of `jsonencode()` for Inline Policies***
Using Terraform's native `jsonencode()` function for the policy document avoids the need for separate `.json` files or `data` blocks, keeping the resource self-contained and reducing the number of files to manage. It also ensures the JSON is syntactically validated by Terraform before the API call is made.

***LocalStack for Pre-Production Testing***
All endpoints are redirected to LocalStack (`http://aws:4566`), enabling full Terraform lifecycle testing without incurring AWS API costs or risking changes to production infrastructure. The `skip_credentials_validation` and `skip_requesting_account_id` provider flags are correctly scoped to the LocalStack provider block and should be removed when targeting real AWS accounts.

## Lessons Learned

**1. Always inspect `provider.tf` before authoring resources.** Understanding the endpoint overrides, provider version, and any non-standard flags (such as `skip_credentials_validation`) is essential before writing resource definitions. In this implementation, confirming LocalStack was the target prevented attempting to use real AWS credentials.

**2. The `-auto-approve` flag should be used deliberately.** In this controlled LocalStack environment it was appropriate, but in production workflows `terraform apply` should always be run without `-auto-approve` to allow human review of the plan output immediately before execution. Consider using `terraform plan -out=tfplan` followed by `terraform apply tfplan` to ensure apply executes exactly the reviewed plan.

**3. `terraform state list` is not sufficient for production verification.** Terraform state reflects what Terraform believes to be true. An independent CLI query (`aws iam list-policies`) confirms the resource was actually created in the target infrastructure layer. Both checks together constitute a complete verification.

**4. Wildcard action patterns require careful scope consideration.** `ec2:Describe*`, `ec2:Get*`, and `ec2:List*` are broad patterns that will automatically include any new EC2 read actions AWS introduces in future API versions. This is generally desirable for read-only policies but should be reviewed against compliance frameworks (e.g., CIS Benchmarks, SOC 2) to ensure no unintended data exposure.

**5. The `AttachmentCount: 0` result is expected but noteworthy.** A policy with zero attachments has no operational effect. The next step in a complete IAM configuration workflow would be attaching this policy to the appropriate IAM user, group, or role.
